# ADR-0004: 外部HTTPのテストを WebMock の固定スタブで行う

## ステータス
承認済み / 2026-07-25

## 背景
`FeedFetcher` は外部のフィードにHTTPで取りにいきます。この通信をテストでどう扱うかで、CIの再現性が決まります。とくにタイムアウトや不正XMLといった異常系こそ、確実に再現できる形でテストしたい状況でした。

## 決定
WebMock で実ネットワークを遮断し（`disable_net_connect!(allow_localhost: false)`）、RSS/Atom の fixture を固定スタブとして返します。正常系に加え、タイムアウト・404・500・不正XML・非フィードXML の異常系を明示的にテストします。

## 検討した選択肢

**実通信** — 本物のレスポンスに当たれるのが利点。欠点は、CIが外部サイトの生死とレート制限に左右され、再現性がないこと。異常系は狙って起こせず、相手を落とすわけにもいきません。

**VCR** — 初回に実通信を記録し以降は再生するので、実レスポンスに忠実なのが利点。欠点は、カセットという別の管理対象が増えること。記録は陳腐化し、秘匿情報の混入にも気を配ることになります。この規模では割に合いません。

**WebMock + 固定スタブ（採用）** — 実通信がなく、応答を完全に制御できます。異常系も1行で作れます。対価は、スタブが本物のフィードから乖離しうることです。fixture を実在の形に寄せて抑えます。

## 根拠
異常系を確実に再現できることを最優先しました。タイムアウト・500・途中で切れたXMLは、実通信では安定して起こせません。ここはこのアプリの信頼性の要で、`FeedFetcher` は失敗を種類ごとに別の例外へ振り分け、feed 行に記録しています。その分岐を1つずつ突けることに一番の価値があります。VCR の「実レスポンスへの忠実さ」は魅力ですが、カセットの管理コストには見合いません。この規模では固定スタブの方が総量が少なくて済みます。

## 影響
スタブは手で書いた想定なので、実在フィードの想定外の書式は取りこぼす場合があります。それはテストではなく、実際に落ちたフィードの fixture を1つ足す形で埋めます。フィード取得のHTTP層を差し替え可能に切り出すときも、この遮断方針は土台として残ります。
