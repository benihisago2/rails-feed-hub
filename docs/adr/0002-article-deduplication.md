# ADR-0002: 記事の重複排除をデータベース制約で行う

## ステータス
承認済み / 2026-07-25

## 背景
同じフィードを繰り返し取得すると、前回と同じ記事が何度も返ってきます。二重登録を防ぐ仕組みが要ります。しかも取得はフィード単位のジョブとして並列に走り、手動の再取得と定期実行が重なることもある。並行実行を前提に設計する必要がありました。

## 決定
`articles` に `(feed_id, guid)` の複合ユニークインデックスを張り、保存は `upsert_all`（`INSERT ... ON CONFLICT`）で行います。guid はフィード内でのみ一意なので、記事の同一性はこのペアで表します。

## 検討した選択肢

**アプリ側の存在チェック（SELECT→INSERT）** — 実装が単純でDDLも不要なのが利点。欠点は、SELECT と INSERT の間に別プロセスが割り込む窓が必ず開くこと。ジョブが並列で走る本アプリでは、手動再取得と定期実行が重なった瞬間に、この窓から重複が入ります。

**DBのユニーク制約のみ** — 重複は確実に防げます。ただし挿入のたびに例外が飛ぶので、既存分と新規分が混ざるフィードでは、例外を1件ずつ捌く扱いにくいコードになります。

**複合ユニークインデックス + `upsert_all`（採用）** — 制約で重複を防ぎ、`ON CONFLICT` で既存行は静かに更新し、新規行だけ挿入します。1回のSQLでバッチ処理でき、並行実行でも競合しません。

## 根拠
重複排除はデータベースの仕事だと決めたのが要点です。アプリ側チェックの「単純さ」は、並行実行という前提の前では成り立ちません。競合を消せるのは制約だけです。Rails のバリデーションは残しますが、それは読みやすいエラーメッセージのためで、保証そのものはDBが持ちます。二重化ではなく役割分担です。

## 影響
guid を持たないフィードには現状 `SecureRandom.uuid` の生成IDを充てているため、取得のたびに新しいIDになり重複排除が効きません。ここは `entry.link` へのフォールバックへ寄せる方向で見直し中です。また guid を同一性の根拠に据えた以上、フィードが発番方針を変えれば別記事として増えます。これはフィード側の仕様であり、こちらでは吸収しません。
