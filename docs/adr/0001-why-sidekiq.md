# ADR-0001: 非同期処理基盤に Sidekiq を選ぶ

## ステータス
承認済み / 2026-07-25

## 背景
フィード取得はHTTP通信を伴い、1件で最大10秒待ちます。リクエスト内で同期処理すれば、フィードの数だけ待ち時間が積み上がります。取得は定期的に、かつフィードごとに独立して走らせたい。その実行基盤を決める必要がありました。

## 決定
Sidekiq を採用します。取得は「全フィードを1ジョブ」ではなく `FetchFeedJob`（1フィード = 1ジョブ、引数は `feed_id`）に分け、`ScheduleFeedFetchesJob` が1時間ごとに各フィード分をキューへ積みます。

## 検討した選択肢

**Active Job の `:async` アダプタ** — 依存もインフラも不要なのが利点。欠点はキューがプロセス内メモリにあることで、再起動で未処理ジョブが消え、retry・dead set・可視化もなく、Puma のスレッドを奪い合います。運用には乗せられません。

**Solid Queue** — DBにジョブを持つので永続化はされます。ただし本アプリは Sidekiq のために Redis を立てています。定期実行（sidekiq-cron）と成熟した retry を同じ Redis 上で使える以上、別系統を増やす理由はありません。

**Sidekiq（採用）** — retry・dead set・Web UI が最初から揃い、cron も同じ基盤に乗ります。対価は Redis という運用対象が1つ増えることです。

## 根拠
核はジョブの粒度をフィード単位にした点です。全フィードを1ジョブにすればエンキューは1回で済みます。一方で1件のホストが落ちるだけで全体が失敗し、retry のたびに成功済みまで取得し直します。フィード単位なら失敗はその1件に閉じ、`last_status` と `last_error` もその行に残り、並列に処理できます。エンキュー回数の増加は、この独立性と引き換えにできます。

retry を3回にしたのは、一過性の失敗を指数バックオフで吸収しつつ、直らない失敗は早めに dead set へ送って人目に触れさせるためです。1時間ごとの定期実行が最後の砦なので、回数は欲張りません。

## 影響
Redis が止まればジョブの登録も実行も止まります。ジョブ数はフィード数に比例するため、数万規模になれば、スケジューラの一括エンキューや `:feeds` キューの詰まりを見直すことになります。
